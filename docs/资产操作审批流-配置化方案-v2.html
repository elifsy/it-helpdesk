IT 服务台 · 方案说明 v0.2（配置化）

审批流可配置：按资产、按条件走不同的链

参照钉钉审批的流程设计器，把「谁批、批几层、什么情况跳节点、抄送给谁」全部做成可视化配置；新增一类资产的审批规则不再改代码、不用发版。

2026-11-17 取代 v0.1 的固定链路 状态：待拍板

01v0.2 改了什么

v0.1 给的是「四条写死的链」，这一版把链变成数据：配置出来的流程可以有多条、各自匹配不同资产，条件、节点、抄送都能改。

v0.1 · 固定链路
  • 领用 = 部门负责人 → 资产管理员（写死）
  • 条件只有两个（服务器加节点、借用超 7 天）
  • 想加一条新规则 → 改代码 + 发版
  • 同一业务类型只能有一条链
v0.2 · 可配置
  • 同一业务可挂多条流程，按「适用范围 + 条件」匹配，命中优先级最高的一条
  • 画布式设计器：审批人节点、条件分支、抄送节点自由组合
  • 审批人支持 6 种来源（指定人/部门主管/连续多级/角色/资产管理员/发起人自选）
  • 条件行用「字段 + 运算符 + 值」拼，支持 且/或 分组
  • 改完可「试运行」预演链路，再发布新版本
一条原则：配置描述「规则」，不描述「人」。
节点里只写「申请人的部门主管」「资产管理员」这类角色，具体是谁在运行时按组织数据解析——人员调动、部门换负责人不需要改流程。

03适用范围与优先级

「不同资产走不同流」靠三重匹配实现，越具体越优先。

优先级匹配维度例子适用场景
P100
最高		指定资产（白名单）资产编号 IT-SRV-2024-0001 的核心数据库服务器唯一关键设备，单独定规则
P50业务类型 + 资产分类领用 · 分类 = 服务器 / 网络设备按资产类别差异化管理
P30业务类型 + 条件表达式借用 · 借用天数 > 7 且 资产分类 = 会议室设备同一分类里的例外情况
P10
兜底		业务类型（默认流）领用 · 默认 → 部门负责人 → 资产管理员没有更具体规则时使用

匹配顺序（运行时）

  1. 取「业务类型」匹配、且状态为启用的全部流程，按优先级降序。
  2. 逐条判断适用范围：指定资产命中 → 直接采用；分类集合命中 → 判断条件表达式。
  3. 条件满足的第一条即为本次实例使用的流程；流程内再按分支顺序匹配，命中第一条分支。
  4. 全部未命中 → 用该业务的「默认流」；默认流不存在则单人审批（资产管理员）。

保存模板时自动做重叠检测：两条同优先级、同适用范围且条件区间重叠时提示「可能冲突」，避免上线后不确定走哪条。

04条件变量与表达式

条件行的左边是变量，全部来自系统已有数据；标 需扩展 的是要补字段才能用的。

变量类型取值来源示例用法
bizType枚举领用/借用/更换/归还= 领用
asset.category枚举（多选）资产台账分类∈ [服务器, 网络设备]
asset.no文本资产编号= IT-SRV-2024-0001
asset.status枚举在用/闲置/借出中…= 闲置
asset.inWarranty布尔warrantyEnd 是否晚于今天= 否（过保设备更换需多一层）
asset.ageMonths数字buyDate 到今天的月数> 60（用满 5 年）
asset.value数字资产原值 需扩展（台账加字段）≥ 8000
request.borrowDays数字预期归还日 − 今天> 7
applicant.dept组织申请人部门= 生产部
applicant.deptLevel数字部门在组织树中的层级≥ 2（二级部门以下）
applicant.crossDept布尔资产当前使用人部门 ≠ 申请人部门= 是（跨部门借用要多批一层）
applicant.role枚举USER/IT/ADMIN≠ IT
request.qty数字申请数量 需扩展（当前一单一台）> 1

运算符

等于 / 不等于 / 包含任一 / 不包含 / 大于 / 小于 / 大于等于 / 小于等于 / 为空 / 不为空；布尔值直接用「是 / 否」下拉。

组合方式

条件组 = 若干行 + 行间关系

行与行之间可选「且 / 或」（同一组内统一关系，和钉钉一致，避免理解成本）。需要混合逻辑时拆成两个分支，用分支顺序表达优先级。

举例：asset.category ∈ [服务器,网络设备] 且 asset.inWarranty = 否 → 「服务器过保领用」独立分支，多一个 IT 主管节点。

条件行示意：左侧字段、中间运算符、右侧取值，行间用且/或连接

为什么不做自由公式

像 (A 且 B) 或 C 这种嵌套，配置人容易写错、事后难排查。用「多分支 + 顺序」等价表达，且能直接在画布上看出优先级。

条件为空

不填条件的分支即「默认分支」，必须放在最后一条，否则保存时报错。

保存时的自动校验

  • 流程必须有且只有一个「结束」节点，且至少一个审批节点；
  • 条件分支最后必须存在默认分支；字段类型与运算符不匹配（如文本用「大于」）直接报错；
  • 同业务、同优先级的适用范围重叠 → 提示「可能冲突」，要求调整优先级；
  • 引用了不存在的角色/部门 → 标黄提醒，允许保存但不能发布；
  • 发布前强制试运行一次（可跳过，但会记录跳过人）。

11版本、灰度与执行

版本快照

流程每次发布生成新版本（v1→v2）。提交时把「版本 + 节点链」快照写进实例，新版本只影响之后提交的单，在途单据按原版本跑完，与钉钉一致。

草稿与灰度

模板可存草稿不影响线上；可只对某部门/某人开启（灰度名单），先跑一周再全量。

停用与回滚

停用后不再匹配新单，在途继续；支持一键回滚到上一版本（保留审计记录）。

执行动作可配

末节点通过后执行什么：绑定使用人 / 回库置闲置 / 回收旧机并把未结工单转移到新机。沿用现有 AssetRequestService 的执行逻辑，配置只决定「走哪条链」。

引擎执行流程（伪代码）

flow   = matchFlow(bizType, asset)          // 优先级 → 适用范围 → 条件
branch = flow.branches.firstMatch(asset, request)
nodes  = branch ? branch.nodes : flow.defaultNodes
instance = saveSnapshot(flow.version, nodes)
for node of nodes:
    people = resolveApprovers(node, applicant, asset)   // 角色/主管/连续多级…
    if people.isEmpty():
        if node.emptyPolicy == SKIP: markSkipped(node); continue
        if node.emptyPolicy == TO_ADMIN: people = admins();
        else: reject("审批人为空")
    createTasks(node, people, node.mode)                // 或签/会签/依次
    notifyDingTalk(people, actionCard(url="/#/approvals/task/{id}"))

A附录：能不能直接用钉钉审批？

能，而且我们现有凭据已经够用——系统里已经是一个钉钉企业内部应用（corpId / appKey / appSecret / agentId 齐全），发起审批实例复用同一个 access_token，不需要新建应用。

结论先说
可行，且开发量比自研设计器小得多。但建议走混合模式：申请单还在我们系统填（资产选择、库存校验、防重复提交都在我们这），提交后由服务端去钉钉发起一条审批实例；审批人在钉钉审批里批，结果通过定时轮询同步回来，由我们执行资产动作。这样既拿到钉钉原生的待办与提醒，又不用把资产台账搬进钉钉表单。

三条路，差别在「表单在哪、结果怎么回来」

路线做法优点代价
B1 纯钉钉审批 审批模板、表单全在钉钉审批后台建，员工直接在钉钉审批里发起。 零开发（只做结果同步）；管理员自助改流程 钉钉表单里选不了我们的资产台账（只能填编号字符串），库存校验、防重复提交、采购/维保全丢；报表要另做
B2 混合（推荐） 我们系统填单 → 服务端调「发起审批实例」把资产快照写进实例表单（只读文本字段）→ 钉钉里审批 → 轮询/订阅回写状态 → 我们执行资产动作 审批体验原生（待办、DING、审批中心统一）；开发集中在发起与同步两处 钉钉侧要建模板、给应用开审批权限；表单字段是钉钉的字段类型，展示受一定限制
B3 宜搭/低代码 用宜搭做表单与流程，我们的系统只做资产台账同步。 改表单不改代码 需宜搭授权与账号数；与台账双向同步更复杂，维护两套主数据

混合模式的链路

结果怎么回来：两条路，内网只能选一条

方式机制时延前提
定时轮询每 1–2 分钟拉一次「进行中实例」的状态，变了就回写并执行1–2 分钟只需出网、不需要公网入口，内网部署可选
事件订阅钉钉在审批状态变更时回调我们接口秒级回调地址必须公网可达 + 验签；内网需穿透或网关反代

建议先用轮询（量和延迟都能接受），将来有了公网入口再切订阅，业务代码不用改——两种方式都走同一个「实例状态同步」函数。

A.1 如果用事件订阅，具体会是这样

钉钉在审批状态变化时主动回调我们的接口，秒级知道结果。但它不是「把轮询换掉」，而是「在轮询前面加一条快车道」——兜底轮询仍然要留。

必须先解决的 6 个问题（否则不建议上）

问题会发生什么怎么处理
公网入口钉钉回调打不进内网，一条事件都收不到服务器要有公网域名 + 443 证书（nginx 反代一个路径）；没有公网就用内网穿透，但穿透掉线＝事件全丢
3 秒超时回调里同步跑业务（改资产、发通知）容易超时，钉钉判定失败并重试，事件堆叠收到即入队、立刻返回 success，业务异步执行
事件重复 / 乱序同一审批被处理两次 → 资产被绑定两次、履历写两条it_dingtalk_event 用 event_id 唯一索引；实例状态只允许前进（RUNNING→COMPLETED 不可回退）
加解密与验签aes_key / token 配错，回调静默失败，日志里只有密文，很难查写一个「本地自测脚本」用同样算法加密一条样例，联调前先跑通；密钥变更要有记录
事件信息不全事件只给实例 id 与结果，没有审批意见、节点人入队后再调一次「查询实例详情」补数据（一次出网调用），失败的进重试队列
安全面变大一个无需登录的公网接口，可能被扫描与伪造请求验签 + 时间戳窗口 + 限流 + 只接受钉钉事件格式；不返回业务数据

订阅 vs 轮询，怎么选

维度事件订阅定时轮询
回写时延秒级，员工几乎和审批人同时收到结果1–2 分钟
公网要求必须公网可达 + 证书只需出网
可靠性钉钉会重试，但仍有最终丢失可能 → 仍需兜底只要服务在跑就不会漏
实现复杂度验签、解密、幂等、异步队列、重试表一个定时任务 + 幂等
接口限流影响无（对方推我们）有几毫秒级调用，量很小，基本不受限
运维/排障要盯回调到达率、证书到期、穿透稳定性看任务日志即可
工程上的正确做法：两条都要，订阅加速、轮询兜底。
订阅把「审批通过 → 资产状态更新」压到秒级；每 10 分钟扫一次「钉钉仍 RUNNING 但本地记录了超过 5 分钟未同步」的实例，把漏掉的事件补回来。这样即使回调地址挂一天，数据也不会错，只是慢一点。

落地顺序建议：先轮询跑通闭环（1 天内可验证），确认整套「发起 → 审批 → 回写 → 执行」正确之后，再把订阅接在同一个「实例状态同步」函数前面。这样即使订阅环境没准备好，功能也是可用的。

和自研方案的真实差距

维度自研（本方案 01–15 节）用钉钉审批
审批体验卡片深链跳 H5 再点通过钉钉原生待办，在钉钉里直接批，还能用 DING、审批中心
流程配置我们做设计器，配置在系统内钉钉审批后台配，管理员自助，但受钉钉表单字段限制
资产选择台账联动、库存实时校验钉钉表单里选不了台账（B1 只能填编号；B2 由我们代填，体验保持一致）
审批中设备被抢执行时二次校验，失败退回重选钉钉不知道库存变化，只能靠我们执行时兜底（这点 B2 也一样）
权限体系复用 request.approve / 新权限点审批人由钉钉流程决定，需与我们权限做映射和核对
数据归属全在我们库，报表随便做仍需把实例结果落库，否则报表要跨系统取数
开发量（P0）引擎 + 设计器 + 页面（较大）发起 + 同步 + 页面改造（明显更小）
对外依赖无依赖钉钉管理员配模板、开审批权限；断网/接口限流要兜底

走钉钉需要准备的清单

#事项说明
1开放平台给应用勾选「审批」权限现有应用加权限点即可，不需要新建应用
2钉钉管理员建 4 条审批模板领用 / 借用 / 更换 / 归还，各返回一个 processCode 配到我们系统
3确认模板里放哪些只读字段建议：申请单号、资产编号/名称/分类/位置、申请人、事由、借用天数
4字段映射表我们字段 → 钉钉表单控件（文本/数字/日期），一次配好存库
5同步任务定时轮询实例状态；幂等键用申请单号，重复同步不重复执行
6状态映射钉钉 RUNNING/COMPLETED/TERMINATED → 我们 APPROVED/REJECTED/CANCELLED
7兜底钉钉接口失败：本地照常记 PENDING，重试队列 + 告警；钉钉故障时可切换「系统内审批」应急

我的建议

如果诉求是「审批集中到钉钉、管理员自己改流程、少写代码」

走 B2 混合：我们只做「发起 + 同步 + 执行」，设计器整块省掉。P0 工期明显缩短，且审批人不用学新页面。

如果「资产选择、库存一致、内网无外网、自定义报表」是硬约束

走 自研：所有逻辑闭环在我们库，审批在大屏/手机上都可做，代价是要自己做设计器与提醒链路。

两者不冲突：先把「审批实例 + 节点任务 + 状态同步」这套表建起来，它是两条路的公共底座——自研引擎往里写，钉钉同步也往里写。以后想换，只换发起与同步适配层，页面和资产动作都不用动。

下一步可选：先做 2 天技术验证（PoC）
用现有应用凭据 + 一条测试审批模板，跑通「发起实例 → 钉钉里审批 → 轮询拉回结果」这条链，同时确认三件事：审批权限是否已开、模板能否由管理员建、轮询频率是否被限流。验证通过再定 P0 走哪条路，避免方案层面的空转。
